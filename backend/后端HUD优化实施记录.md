2026-11-12 · 基线为本机已核对的 GitHub 后端 v0.9，源码快照来自 `6b1f0de`。GitHub 比较显示该基线的后端包含 `ebb2ed3` 日志修复。本轮在独立目录实施。

## 用户确认

- 审计故障沿用现有保护策略。C8 的降级继续飞行和审计队列分级列入后续讨论。
- 运动报文过期沿用 `PROTECTED`，心跳不续期运动。

## 已优化的部分

| 方案 | 已落地的改动 |
| --- | --- |
| C1、C2 | 位置、速度、姿态、角速度带上 `age_ms` 和 `reason`。本地测量按三个采样周期判过期，20 Hz 时是 150 ms。样本序号沿用原字段。 |
| C3 | 统一状态补上保护原因、恢复窗口、目标航向和仿真环境。阻塞项由核心给出，包含 `ALTITUDE`、`RADIUS`、`SPEED`。归中确认由实际操作提供，边界阻塞项只描述可测的动力学条件。 |
| C4 | 补上 `control.active`、`awaiting_neutral` 和 `last_applied`，最近应用序号只记录执行成功的运动，切换轮次时清除。 |
| C5、C6 | 视频沿用原取值。服务退化返回明确分类，保留原始错误码。对于运动报文，`RETRY_LATER` 表示等服务恢复后由用户发起新意图。 |
| C7 | 仿真线程一次发布完整状态，内部读取无需持有发布锁。配置按版本复用，统一 SSE 帧由每个服务的发布线程共享转换。逐机旧接口继续提供 `instance_config`。 |
| C8 | 维持审计故障保护。修复了飞机已锁存其他保护时，审计故障反复刷新轮次的问题。 |
| C9 | 独立模式 SSE 由共享发布线程收集，目标 25 Hz。无状态变化发注释心跳。用 `Last-Event-ID` 恢复最近 50 帧内的状态，过期或服务重启后发送重同步标志与最新帧。另提供可选 `focus`。 |
| C10、C11 | 身份与可写设备继续从 `capabilities` 获取。设备目录公开配置来源，健康接口公开实际步频、步长抖动 p99、采样数及迟于计划至少一个步长的次数。 |

## 与 GitHub APP 的对照

已读取 [PR #4](https://github.com/czy2024333-spec/AppRemoteControlProject/pull/4) 的 `4dd149a`。横屏 HUD 使用逐机 `RotorState` 的 `environment`、`boundary_recovery` 等原字段。总览通过 `UnifiedRepository` 读取全机统一状态，当前仍以整机新鲜度为主。客户端允许未知 JSON 键，SSE 只处理带 `data:` 的行。旧请求继续得到全机完整帧。

请求 `GET /api/v1/events?focus=sim-drone-2` 时，目标机每帧返回完整状态，其他成员约 10 Hz 返回位置、实际偏航、模式、新鲜度。仅在 `peers_included=true` 时更新僚机，其他帧应保留各自上一份样本，并按时间判过期。历史帧带 `replayed=true`，可用于补轨迹。连接失效或恢复后仍由当前状态和控制流程判定能否操纵。偏航零点为世界 X 正向，绕 Z 正轴逆时针为正。

旧客户端继续使用原路径。白名单网页可预检并发送 `Last-Event-ID`，连接与每次 GET 都沿用现有鉴权。

## 复审后的改动和问题

- Windows 11、CPython 3.13.14 下确认 2 ms 的 `Event.wait()` 明显超时。改用 `time.sleep()` 短等待，三次对照中三机抖动 p99 的中位数从 15.12–16.81 ms 降到 0.96–1.06 ms，改后控制回执 p95 为 4.70–5.00 ms，四端 SSE 实收 24.98–25.02 Hz。逐机最小值／中位数／最大值见 [后端架构逻辑说明](后端架构逻辑说明.md)。
- SSE 发布线程异常或卡住时结束订阅，健康接口暴露原因。PR #4 已有独立的 500 ms 新状态超时，保留注释心跳。`capabilities` 新增五项布尔标志，契约仍为 1.0。
- 新回归确认 STOP 轮次、模式和按 ID 查询的回执，统一 `protection.recovery` 和旧逐机 `boundary_recovery` 在同一发布序号上相等。跨动作复用同一离散 ID 曾错误返回上一个动作的回执，已加入动作路径校验。审计恢复需要重启和主动建立新会话。后端 131 项通过，动力学 26 项通过、1 项按条件跳过。[基线后端回归摘要](../docs/validation/后端HUD_20261112_验证摘要.json) · [基线动力学回归摘要](../docs/validation/后端HUD_20261112_验证摘要.json)
- PR #4 固定版本的 25 项 JVM 回归通过，其中两项新增用例验证单机和总览收到注释心跳时仍按新状态时间过期，以及新增能力标志的解码。
- UE 和旧联调页的 SSE 解析不依赖 `id` 行位置。UE 健康检查所需的 `boot_id` 已补齐。UE 的 `EventsPath` 和旧联调页仍须按独立模式选择相应路径。PR #4 后续需验证重连首帧超时、接入新状态字段，并完成手机局域网刷新和延迟验收。

## 2026-11-15 · 独立三机流畅度

11 月 14 日联调日志有 940 条 2 号机运动受理记录。同一控制轮次和操纵意图内，受理间隔 P95 为 186.85 ms，最长 398.16 ms。日志还记录了两次水平参考边界保护、一次 `INPUT_TIMEOUT`。受理间隔取自服务端审计，无法单独给出手机调度或无线链路耗时。

在 50 Hz 动力学、25 Hz SSE 下，相邻 HUD 样本通常应相差两步，即 40 ms。Windows 上按绝对时刻短睡后，三轮 24 秒对照中，HUD 实收间隔相对 40 ms 的绝对偏差 P99 中位数由 11.82 ms 降至 2.72 ms。后续一次 60 秒试验仍出现 1 号机仅 51.6% 的相邻样本恰好相差 40 ms。发布时刻接近该机的动力学步进，读到的步号可能交替跨一或三步。[短等待对照数据摘要](../docs/validation/后端三机_20261115_验证摘要.json)

共享发布线程现在根据各成员的计划步进时刻选择取样点，统一步频且一个发布周期包含整数个步长时，选各机预计完成时刻之间最大的空档。预留 2 ms 估计步进到状态就绪的耗时。计划步进重新计时或发布错过一个完整周期时重新选点。其他步频组合按固定 25 Hz 发布。位置、速度、姿态仍来自对应步号的仿真真值。紧凑 SSE JSON 去掉结构空白，一份实测全机样例从 9,759 字节降至 8,986 字节。

压测分别记录后端队列及应用耗时、HTTP 往返、服务端发帧间隔、客户端实收间隔和逐机仿真时间差分。用现有来源凭据查询 `GET /api/health`，在 `data.state_publisher.cadence` 查看最近共享取样的 P95、最大间隔和最新帧年龄。

最终 60 秒混合负载中，8 路 SSE 各收到 1,500 帧。三路逐机 HUD 每路的 1,498 个同连接样本间隔在仿真时间上均为 40 ms。重连耗时单独计量。以 40 ms 为目标，三路 HUD 实收间隔的绝对偏差 P99 为 3.35–3.58 ms。3,572 条运动回执的逐机 HTTP 往返 P95 为 5.57–5.74 ms，逐机后端排队与应用 P95 为 2.74–2.90 ms。60 次健康检查和 4 次日志导出均成功。50、55、100 Hz 混合步频另跑 8 秒，8 路 SSE 实收 25.00–25.13 Hz。[60 秒复测摘要](../docs/validation/后端三机_20261115_验证摘要.json) · [混合步频复测摘要](../docs/validation/后端三机_20261115_验证摘要.json)

后端 154 项和动力学 26 项通过，另有 1 项历史产物检查按默认条件跳过。前一次失联注入回归曾在健康成员上遇到 `STALE_EPOCH`，单项复跑和最终全量检查均通过，偶发拒绝的触发原因待确认。[后端回归摘要](../docs/validation/后端三机_20261115_验证摘要.json) · [动力学回归摘要](../docs/validation/后端三机_20261115_验证摘要.json)

手机端复测时，在同一个局域网重启本版后端，用 2 号机在场地中间持续轻推同一方向再松杆。记录出现卡顿的时间、后端健康响应和 APP 的接收、状态提交统计。现场出现的长指令间隔仍待定位。地图、姿态仪的显示帧间插值需要在 APP 或 UE 的绘制层验证，保护和模式以原始状态为准。

## 2026-11-20 · 局部 GNSS 采样与有效期

20 Hz GNSS 在 50 Hz 动力学下原先交替采到 40 和 60 ms 的时间间隔。改为按 GNSS 时刻插值后，连续 100 个采样间隔均为 50 ms。传输延迟从采样点计算，噪声与丢包分别使用可复现的随机序列，过期判定修正了毫秒换算的浮点尾差。三机开启模拟误差运行 30 秒，8 路状态推送各实收 24.97–25.00 Hz。采样间隔统计取自仿真时间，推送频率取自本机客户端收帧。[对照实验、回归及待办](GNSS误差模拟_初步实现.md)
