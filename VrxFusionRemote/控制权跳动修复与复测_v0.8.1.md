# v0.8.1 控制权跳动修复与复测

2026-10-20。前端覆盖升级，兼容现有v0.8统一后端；后端、UE源码均未修改。

## 现场结论的边界

用户提供的《控制权退回观察_排查_20261020》记录了三次INPUT_TIMEOUT：运动指令已经停发，心跳仍被确认，保护前没有已确认的停止。记录能证明这一现象，尚不能单独确定手机停发的具体触发点。

“正在观察，尚未接管”表示客户端未处于READY，不等于登录角色变成观察员。v0.8目前仍是来源Token认证，正式用户角色未接入。

## 本次修复

- 松杆时取消未返回的旧运动HTTP请求，使停止请求不必等待旧运动请求的完整网络超时；仅取消运动请求，不误取消心跳。
- 心跳周期从固定100ms改为`min(100ms, 设备TTL/4)`并扣除本轮发送耗时。100ms配置下松杆后仍以约25ms周期维持来源租约；心跳仍不延长运动输入的有效期。
- 状态、能力或来源失效，以及运动/心跳发送失败时，撤销控制；若此前正在运动，独立尝试提交停止。停止失败明确保留“停止未确认”，后端TTL保护继续兜底。
- 主动取消的旧运动请求不再当作新故障撤销正常停止后的控制权；迟到回执不恢复旧运动。
- 松杆STOP会更新后端控制轮次。只在本次STOP等待应答且来源仍为APP、模式为HOLD时暂缓判定轮次变化；HTTP确认后一起更新轮次和步号。保护或来源改变仍立即撤销，STOP失败也撤销，避免把自己的停止误判成外部抢权。
- 控制失效原因保留到用户重新申请成功；目录刷新错误不会被下一帧正常SSE清掉。诊断事件补充失效原因、当时步号、模式和来源，以及停止请求/确认。
- 保护提示优先于只读提示；显示INPUT_TIMEOUT原因。能力不可用时不启用操纵或解除保护。
- 继续要求主动接管、真实松手和归中；不关闭TTL、不用心跳延长运动、不自动恢复控制或重发旧杆值。

## 手机覆盖更新

1. 安装本包的`旋翼遥控APP-v0.8.1-覆盖更新.apk`。保持现有应用包名和签名，无需卸载旧版。
2. 后端继续使用v0.8的`--mode unified`，手机与电脑在同一局域网。地址为`http://电脑IPv4:8765`，开发APP来源Token为`demo-app-token-2026`。不要把来源Token填写成用户角色。
3. 进入单机操纵，连接后先观察。打开原设置页的连接分类，在“性能与持续运行记录”中填写手机和局域网条件，点击“开始记录”，再关闭设置。

## 按顺序复测

1. 双杆松开，主动申请控制；等待“控制就绪”。在空旷仿真范围内小幅水平推杆3～5秒，松杆后应悬停且保留控制。左右各做几次，避免一直朝同一方向触碰边界。
2. 双杆交替操作、短推后松手。正常松手不应反复要求重新申请，不应因为停止请求被旧运动应答堵住而触发INPUT_TIMEOUT。
3. 打开设置再返回：打开时停止运动，关闭后不能自动恢复之前杆值。重新推动才允许运动。
4. 测试保护：点“保护”，松开双杆，确认解除，然后主动重新申请；解除保护本身不会恢复READY。
5. 测试断网/APP转后台：此时停发并失去控制属于预期安全行为；网络恢复或切回APP后仍需主动申请。断网时停止不一定到达，因此不能把客户端“停发”当成后端“已停止”。
6. 如果再次跳动，先记下提示里的具体原因，不反复点接管；松手，截图，然后在设置中结束记录并导出JSONL。提供手机型号、发生时间和记录，与后端相同步号/时间核对。

## 正常状态与异常状态

| 显示 | 含义与操作 |
| --- | --- |
| 控制就绪／正在操纵 | 当前申请已确认，可操作；松杆提交停止 |
| 正在观察，尚未接管 | 尚未申请或已经释放，需用户主动申请 |
| 当前只读，操纵未启用 | 来源、能力或目录校验不满足；查看具体原因 |
| 状态失效，操纵已暂停 | 两条状态链路之一过期、离线或无效；恢复后重新申请 |
| 上一次操作未完成 | 查看保留的失效原因；确认安全后松手重新申请 |
| 保护已锁存 | 先松手并满足恢复条件，解除后再主动申请 |

## 仍需现场确认

本机HTTP回归不能代替这台手机的手势、界面帧、Wi-Fi、系统后台限制和长时间测试；现场三次停发是否还有其他触发点，须用更新版记录复测。实际硬件、真实UE画面、约定局域网性能和4小时验收不在本次修复测试结论内。
