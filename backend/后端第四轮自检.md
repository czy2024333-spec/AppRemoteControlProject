## 执行队列与集群批量历史

| 项目 | 修复前 | 修复后 |
| --- | --- | --- |
| 逐机队列积压 | 注入 128 个普通待执行项，STOP、PROTECT 都返回 `503 QUEUE_FULL` | 普通请求的入队阈值为 128。STOP 和断连可再使用 8 个位置，PROTECT 和管理器内部屏障可使用最末 4 个位置。总容量为 140。 |
| 旧集群批量历史 | 用真实 HTTP 填满 2048 条后，批量 STOP、PROTECT 均返回 `503 HISTORY_FULL`，三架飞机仍处于 `ACTIVE` | 每来源集群会话另存最近 64 个纯安全批次结果。普通历史满额时，合法的 STOP、PROTECT、断连仍可按目标成员分发。 |

修复前证据分别来自逐机提交入口和本机旧集群 HTTP 服务。修复后再次用真实 HTTP 写满 2048 条普通历史，批量 STOP、PROTECT 分别使三机进入 `HOLD`、`PROTECTED`，新普通请求继续收到 `HISTORY_FULL`。队列复现见本机 `results/doctor/round4-before-queue.json` · 旧集群修复前见本机 `results/doctor/round4-before-cluster.json` · 旧集群修复后见本机 `results/doctor/round4-after-cluster.json`

入队优先级由动作及已发布配置决定。执行时仍检查当前权限、来源、会话、序号、TTL 和轮次。优先队列在普通积压前执行安全动作，已开始执行的请求会先结束。对应预留也占满时仍返回 `QUEUE_FULL`，诊断可用 `--doctor` 查看实际容量。旧集群批量分发仍需取得管理器锁，单机安全入口沿用现有直接提交路径。容量诊断见本机 `results/doctor/round4-capacities.json`

旧集群纯安全批次仍须提交完整当前成员集合、有效 `selection_id` 和成员报文。含普通动作的混合批次按普通历史处理。安全批次保留逐成员结果，包含 `PARTIAL`。同 `request_id` 同内容返回原结果。更换内容返回 `REQUEST_ID_REUSED`。记录滚动换出后，原批次序号返回 `STALE_CLUSTER_SEQUENCE`。

## 原清单第 11 项的补测

测试工具沿用同一台机器的三机隔离服务。八条 SSE 包括四路全机订阅、三路逐机 HUD 订阅，以及一路按旧字段读取的 UE 兼容客户端。三个操纵端继续约 20 Hz 发送运动并定期发心跳，同时轮询 `/api/health` 和导出 JSONL。所有 SSE 连接在测试中途集中重连。

```powershell
python run_backend.py --mode independent --doctor
python run_checks.py
python run_independent_acceptance.py --mixed-load --seconds 60 --out results/independent-round4-repeat
```

`step_compute_ms` 记录单次 `core.step()` 的墙钟耗时。`step_interval_abs_error_ms` 记录实际步进间隔相对标称 20 ms 的绝对偏差。两者与控制回执均统计 P95、P99、P99.9 和最大值。CPU 采用进程 CPU 时间除以墙钟时长，以单核心为 100%，包含同进程的测试客户端。

首轮三机控制和八路 SSE 正常，使用相对 `--out` 路径时日志导出返回 `400 INVALID_ARGUMENT`。短复现定位为 SQLite 只读连接尝试将相对路径转换为文件 URI。现在独立服务在打开结果目录时解析绝对路径，原相对启动方式仍可使用。日志 HTTP 回归也改为用相对目录启动。首轮失败记录见本机 `results/independent-round4-mixed-60s/summary.json` · 错误定位记录见本机 `results/independent-round4-mixed-debug/summary.json`

修复后的 60 秒本机回环复测通过。三路共确认 3571 条运动、1786 条心跳，控制回执 P95 为 **5.00–5.09 ms**，P99.9 为 **7.81–8.40 ms**，最长 **9.38 ms**。八路 SSE 各收 1500 帧，即 **25.00 Hz**。集中重连到首帧为 **2.67–7.75 ms**。60 次健康检查与 4 次日志导出均成功，最大导出约 **1.06 MiB**。[修复后复测摘要](../docs/validation/后端三机_20261115_验证摘要.json)

| 指标 | 1 号机 | 2 号机 | 3 号机 |
| --- | ---: | ---: | ---: |
| `core.step()` P99.9 | 2.74 ms | 2.92 ms | 3.95 ms |
| `core.step()` 最大值 | 3.07 ms | 3.77 ms | 4.76 ms |

进程 CPU 折算为单核 **44.7%**。2 号机偶发的步进间隔偏差达到 29.18 ms。单轮同进程测试无法确认该偏差与日志导出或 GIL 的关系。
