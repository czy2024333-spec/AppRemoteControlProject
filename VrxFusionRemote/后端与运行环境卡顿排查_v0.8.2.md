# 后端与运行环境卡顿排查交接

2026-10-20。仅诊断交接，未修改后端或UE实现。前端修复目录GET连接复用，不放宽运动TTL、状态新鲜度或保护规则。

## 已确认的两个问题

1. **前端目录连接复用缺陷**：目录3秒刷新、服务端HTTP空闲3秒关闭，旧GET复用失效连接后失败，清空目录并停用控制。v0.8.1真实后端测试约8.9秒复现；隔离连接测试复现SocketException。v0.8.2已对只读GET启用连接故障恢复，POST仍不自动重试。
2. **独立的长测卡顿／输入超时**：修复目录后，一轮35秒测试约29秒时INPUT_TIMEOUT；另一轮60秒测试约23.6秒时状态失效、INPUT_TIMEOUT，后端随后记录SCHEDULER_STALL。上述失败时目录仍可写，不能把它归为登录角色变化或继续用目录补丁处理。

测试服务器使用用户v0.8压缩包原样解出的代码，临时端口，3个仿真成员。没有操纵或重启现场服务器。

## 失败轮证据

见交付验证记录中的`long-failed.xml`、`long-failed-control-events.jsonl`及`long-failed-timing.json`。

| 指标 | 失败轮观测 |
| --- | --- |
| 主设备输入TTL | 500ms |
| 目录读取 | 失败前后仍持续成功，可写判断为true |
| 运动HTTP完整回执等待 | 多次约302、374、407、440ms；一次518ms |
| 心跳完整回执等待 | 后续出现约1113～1549ms |
| 成员校验时记录的最大报文年龄 | 约44ms |
| 从成员接收至进入envelope校验的最大等待 | 约30ms |
| 前端处理 | 状态超过500ms／运动失效后撤销控制，尝试停止；没有自动接管 |
| 后端记录 | INPUT_TIMEOUT，随后SCHEDULER_STALL |

成员校验前等待和完整HTTP回执等待的差异，提示需要继续拆分**校验后的执行、状态构建、审计、序列化、HTTP发送、客户端读取／调度**。这些数据还不能直接证明某一个函数是唯一根因。

## 可对照的通过轮

同样3实例和500ms TTL，带时序记录的一轮60秒连续推杆通过：1161条运动输入全部确认，约20轮目录刷新无只读/控制权切换；最长输入接收间隔92.4ms，P95确认上界43ms，最大确认65.9ms。这说明故障具有间歇性，不能拿单轮通过代替稳定性验收。

通过轮给`ClusterManager._audit`加了测试时长记录：1763次调用，最慢约26ms。**该通过轮未证明审计是卡顿根因。** 失败轮仍需同类采样，不能只看源码里有同步写文件就认定责任。

## 后端负责人建议继续检查

- 对`ClusterManager.single_request`及`_single_safety_request`分别记录：等待管理器锁、等待成员应用、`_audit`、生成应答、写完应答的时长。
- 检查`cluster_manager.py`的`_audit`：当前每次打开／关闭JSONL，部分调用在管理器锁内。验证是否偶发磁盘、同步工具或杀毒扫描阻塞；若确认，应把耗时IO移出关键锁和实时控制路径，并明确日志背压与写失败策略。
- 对`app_server.py`的服务循环记录实际调度间隔、命令批处理耗时和动力学耗时，与SCHEDULER_STALL关联；同时记录测试机器CPU、磁盘及内存压力。
- 对服务端确认完成时刻、HTTP发完时刻、APP读取完成时刻进行关联，区分服务器处理慢、应答传输慢、JVM/手机读取与系统调度停顿。
- 分别比较单实例和3实例，但保留3实例失败结果，不用降低负载后的成功代替3实例验收。
- 不通过关闭保护、扩大已约定TTL、把心跳当运动续期或自动重放旧输入掩盖失效。

## 前端已提供的诊断

设置→连接→性能与持续运行记录→开始／结束／导出。新增事件：

- `DIRECTORY_REFRESHED`／`DIRECTORY_REFRESH_FAILED`：目录更新及HTTP/异常类型。
- `MOTION_SEND_GAP`：运动发送间隔超过150ms。
- `HTTP_ACK_SLOW`：某HTTP写请求等待超过150ms。
- `GATEWAY_CONTROL_LOST`／`CONTROL_INVALIDATED`：状态链路、目录、步号及控制失效原因。

记录不写Token或请求正文。发生时应保留手机型号、前后台状态、测试时间和后端同时间段日志。后端修复须保留原权限、控制轮次、停止优先级、幂等及过期拒绝规则，再用同一前端复测。
