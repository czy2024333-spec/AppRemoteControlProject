# 调度卡顿保护修复说明（2026-11-28）

## 一、问题

`SimulationService.run()` 原来用一个条件同时表达"轻微抖动"和"真卡死"：

```python
if now-last>.1 or now-next_tick>.08:
    self.core.protect('SCHEDULER_STALL')
```

50Hz 调度下，操作系统一次正常抖动、磁盘或 GC 停顿都会超过 80ms，保护被反复锁存；
操作员必须不停重新申请控制权，真机联调表现为"连上就 PROTECTED"。

组员前一版改用"1 秒内累计 10 次轻微滞后"去抖，反而把这条误判放大：实测 72 条
`WINDOW_MISSED` 里有 66 条触发当次的 `gap`/`loop` 都低于 80ms，也就是系统完全正常
时也在保护。本版按下面的三档重写。

## 二、判定规则

| 档位 | 条件（`dt=0.02`，即 50Hz） | 结果 |
|---|---|---|
| hard | 单次循环或 tick 滞后 > 500ms | 记 `SCHEDULER_STALL`，锁存保护 + 清除控制通路 |
| streak | 连续 3 次 > 80ms 且累计 ≥ 200ms | 同上 |
| warn | 单次 > 250ms 但未达 500ms | 记 `SCHEDULER_SLOW`，**只审计，不保护** |
| 正常 | 其余情况 | 不动 |

阈值随仿真步长自适应（`backend/stall_guard.py`）：`soft = max(3dt, 80ms)`、
`warn = max(6dt, 250ms)`、`hard = max(10dt, 500ms)`。20Hz 仿真下软阈值自动放宽到
150ms，不需要改代码。

为什么保留 250ms 的留痕档：50Hz 下 250ms 已经丢 12 个控制周期，直接锁存会让正常
机器上的偶发停顿频繁打断操纵；但不留痕又无法在事后判断"到底卡没卡"。所以这一档
只写审计，5 秒限频一次，由日志接口复盘。

另外两处配套改动：

- 卡顿后不再补跑积压的 tick（`next_tick = now + dt`），避免恢复瞬间连续空转再次触发保护；
- `keep_owner`/`selected_source` 之类的"保留控制通路"尝试已撤掉：保护就是清除通路，
  文档也照这个口径写死，不再出现代码与文档冲突。

## 三、审计事件

| event | 触发 | 关键字段 |
|---|---|---|
| `SCHEDULER_STALL` | hard / streak | `gap_ms`、`loop_time_ms`、`missed_cycles`、`reason`、`owner_present` |
| `SCHEDULER_SLOW` | warn | 同上，`reason=SINGLE_SLOW` |

`owner_present` 用来区分"保护时是否真有操作员在操纵"，复盘时先看这一列。

## 四、验证

```bash
cd backend
python -m unittest test_stall_guard -v
python run_checks.py          # 后端 120 项 + 动力学回归
```

`test_stall_guard.py` 覆盖 17 项：稳定空转、2ms+25ms 抖动（上一版误判场景）、单次
120/300/600ms、连续 2/3 次超软阈值、健康轮次重置、软阈值边界、tick 滞后单独触发、
WARN 限频、步长自适应与非法步长。

实测（本机 Windows，`sim_rate_hz=50`）：

- 150 秒连续 10Hz 控制、1191 帧：全程 `ACTIVE`，`SCHEDULER_STALL` 0 条；
- 审计 1200 行（`COMMAND_ACK` 1195 / `MEMBER_STARTED` 3 / `CONTROL_TRANSITION` 2）。

对照上一版：同样负载下没有出现误保护，说明误判已消除；本版另外补上了单次
250~500ms 的可见性。

## 五、待确认

单次 250~500ms 是否要升级为保护（现在只审计）。若要升级，把 `warn_ms` 换成
`hard_ms` 的下限即可，但需要先在目标机器上收集一段 `SCHEDULER_SLOW` 的实际分布，
否则容易回到"频繁锁存"。这条需要负责人拍板，不作为本版默认行为。
